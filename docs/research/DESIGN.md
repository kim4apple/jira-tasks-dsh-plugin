## 一、诊断：为什么现在的详情"又小又挤"

当前详情面板**内联展开在会话输入框下方的一条任务行里**（`conversation.input.dock`）。容器本身就窄，
而面板内部的设计又按"窄容器"写，于是问题层层放大：

| 症状 | 根因 |
|---|---|
| 卡片很矮 | `.jtd-body { max-height: 60vh }` —— 面板自己开了嵌套滚动区 |
| 一列到底、很挤 | `.jtd-grid { grid-template-columns: repeat(auto-fit, minmax(130px,1fr)) }` 在窄容器下退化成单列 |
| 表格要左右拖 | `.jtd-table { min-width: 520px }` —— 在 ~600px 宽的输入框卡片里强制横向滚动 |
| 信息多但乱 | 概要/描述/标签/自定义字段/评论/附件/下载结果 **全部串成一条长列**，没有主次、没有分区 |
| 看不清层级 | 工单号和摘要在 12–13px，跟正文同级 |

**根本问题不是样式，是容器选错了**：把"工单详情"这种**高信息密度的文档**塞进了"输入框下面的小挂件"。

### 2.5 自定义字段的可读化（2026-11-09 实测后落地）

实测你的实例（`jira.s.enlink.top:4443`）：ENDEV-26542 有 **184 个自定义字段、69 个非空**，
而**字段名根本不在 issue 数据里** —— 只在字段定义接口里有。所以：

| 数据源 | 拿什么 | 代价 |
|---|---|---|
| `GET /rest/api/2/issue/{key}?expand=names,schema` | `names`(id→可读名称) + `schema`(id→类型)，**一次请求**，只含本工单有的字段 | 0 额外请求 |
| `GET /rest/api/2/field` | 全实例字段定义（235 条 / 195 自定义），含 `description` | 1 请求，模块级缓存 10 分钟 |
| `GET /rest/api/2/issue/{key}/editmeta` | 该工单类型的配置屏幕字段 | 1 请求 |

**页面呈现：**

```
自定义字段   已填 55 / 共 184    [只看 JIRA 页面上的 17 个]  [显示未填写的 13 项]
──────────────────────────────────────────────────────────────
叙述内容 · 16 项                                  ← 单独成段，正文排版
  技术根因
    退出登录时，网络扩展启停导致网络中断…
  最小复现条件
    黑盒层面能够复现问题的最小执行步骤…
──────────────────────────────────────────────────────────────
结构化字段 · 39 项                                ← 紧凑对照表，单行
  是否有用例            是
  是否影响通用版本      否
  实现差异表            说明功能实现差异
```

- **三档过滤**：空值不占行；JIRA 从帮助文本预填的模板（13 项）默认隐藏、标记「未填写」；
  插件 dump 出来的 Java 对象（开发状态插件的 SummaryBean）直接丢弃
- **字段值按 `schema.type` 渲染**：`array`/`labels` → chip，`date` → 本地时间，`option` → 选项文案
- **按 JIRA 字段顺序排列**（字段定义表原样保序，不排序）

**关于 `screenFields` 的实测结论（决定了默认行为）**：
`editmeta` 只覆盖 69 个有值字段里的 **17 个（25%）**；DC 的 **View Screen 在 REST 里没有任何端点暴露**，
`createmeta` 更差（13/69）。所以 `screenFields` 只当**排序提示**（屏内字段排前面），
默认**不**做硬过滤 —— 否则会藏掉 52 个有真内容的字段，比原生页面信息还少。
过滤是用户点「只看 JIRA 页面上的 N 个」才生效。

## 三、一键「加入当前对话」

### 3.1 交互

详情页顶栏主按钮 **「加入对话 ▾」**，点击展开**选择面板**（popover，锚定按钮，宽 ~400px）：

```
┌──────────────────────────────────────────────┐
│ 加入当前对话                                ✕ │
├──────────────────────────────────────────────┤
│ ☑ 工单详情（字段、描述、最近评论）             │
│                                              │
│ 附件        [全选] [只选日志类]               │
│ ☑ server.log.gz      2.3 MB      已下载 ✓     │
│ ☑ app.log            880 KB      未下载        │
│ ☐ trace.json          12 KB      未下载        │
│ ☑ heapdump.hprof     45 MB       下载失败 ✗   │
│ ☐ core.1234.gz       80 MB      超过上限 🚫  │
│                                              │
│ ⓘ 2 个待下载，共 47.3 MB，下载约需 20 秒        │
├──────────────────────────────────────────────┤
│                    [取消]  [下载并加入对话]    │
└──────────────────────────────────────────────┘
```

- 勾选「工单详情」→ 把字段/描述/最近评论写进对话
- 勾选附件 → **自动下载**并作为文件引用加入对话
- 点「下载并加入对话」后：
  1. 对**未下载**的附件逐个下载（并发上限 3，避免打爆 JIRA）
  2. 已下载的**直接复用**工作区里的文件，不重复下载
  3. 下载成功的 → `conversation.insertFileReferences(refs)` 插成 file chip
  4. 失败的 → 在面板里逐条列出原因，**不影响其他附件**
  5. 同时 `conversation.setDraft(文本)` 写入工单上下文
- 若附件全部失败，仍写入详情文本，并提示"附件下载全部失败"
- **超过大小上限的附件行直接禁用**（不可勾选），提前告知而不是等下载失败

**附件页签里的批量选择**：附件表格每行带复选框，勾选后表格上方浮出「把选中的 N 个加入对话」——
与 popover 走同一套逻辑，两处不重复实现。

**「只选日志类」快捷筛选**：按扩展名 `.log .log.gz .txt .har .json .out .trace .dump` 过滤，
一键勾中最可能是日志的附件。

点击后 **不自动发送**，而是把内容写进输入框草稿，用户确认后再自己发送。

### 3.1.1 附件状态机

| 状态 | 展示 | 行为 |
|---|---|---|
| 未下载 | 文件名 + 大小 | 可勾选；勾选后显示"下载中" |
| 下载中 | 转圈（curl 给不了进度，用不确定态动画） | 不可重复触发 |
| 已下载 ✓ | 文件名 + 大小 + 绿色勾 + 路径 | 复用工作区文件，**不重复下载** |
| 下载失败 ✗ | 文件名 + 红色叉 + 失败原因 | 可重试；不影响同批其他附件 |
| 超过上限 🚫 | 灰显 + 「超过 100 MB 上限」 | **不可勾选** |

### 3.2 技术路径（已确认 DSH 有这套 API）

DSH 的 `conversation` 客户端服务提供：

| 方法 | 用途 |
|---|---|
| `setDraft(text)` | 整体替换草稿（程序化写入，光标落在末尾） |
| `appendDraft(text)` | 在现有草稿后追加段落，保留已有文本与引用 |
| `insertFileReferences(refs)` | 批量插入**文件引用 chip**（`appearance: 'file'`） |
| `send(text)` | 直接发送（**本方案默认不用**） |

文件引用 chip 的字段：`{ source, ref, label, appearance:'file', clipboardText }`。

### 3.4 「结合当前项目做问题定位」

加入对话时额外带上**当前工作区的横向上下文**：

| 带上什么 | 从哪来 | 代价 |
|---|---|---|
| 本工作区配置的项目 Key | 插件已有（按工作区存） | 0 |
| 同项目近 30 天、同组件/同类型的相关工单（最多 5 条） | 一次 JQL 搜索（复用 `/jira/api/search`） | 1 次请求 |
| 该工单的关联/阻塞工单 | `issue.fields.issuelinks`（已在详情里） | 0 |

相关工单只给**工单号 + 摘要 + 状态**三行，不展开详情 —— 给智能体"横向视野"但不撑爆上下文。

## 四、把分析结论写回 issue 评论（v1.8.0，本轮不做）

这是**外部写操作**，而插件一直对外声明"只读，不改 JIRA"。所以这块要设计得比读更谨慎。

```
详情页右栏  [ 写评论 ]
      ↓
┌────────────────────────────────────────────────────────┐
│ 写评论到 PROJ-123                                   ✕ │
├────────────────────────────────────────────────────────┤
│ ┌────────────────────────────────────────────────┐   │
│ │ 结论正文（可编辑）                                │   │
│ │ 根因：登录接口在 token 校验后未处理账号锁定分支…    │   │
│ └────────────────────────────────────────────────┘   │
│ [从当前对话取结论]  [插入模板]        128 / 65535 字  │
├────────────────────────────────────────────────────────┤
│ 提交后不可撤销，将以你的账号 <alice> 发布到 JIRA。      │
│                          [取消]  [提交评论]             │
└────────────────────────────────────────────────────────┘
```

四条硬约束：

1. **必须用户确认**：正文在 textarea 里，**可任意修改**；提交前有二次确认（显示最终字数与开头若干字）
2. **默认关闭**：新增设置项 `allowComment`（默认 **false**）。用户必须显式开启，插件才显示"写评论"入口 —— 避免"一直只读的插件突然能写别人系统"
3. **正文只当纯文本**：不渲染 HTML，不允许在评论里注入标记
4. **可关闭与可撤销**：设置项可随时关掉；提交成功后给出"在 JIRA 查看"链接

正文格式按部署形态分流：

| 部署 | 接口 | body |
|---|---|---|
| **Jira Server / DC**（你现在这套） | `POST /rest/api/2/issue/{key}/comment` | `{"body": "纯文本或 wiki 标记"}` |
| **Jira Cloud** | 同上 | `{"body": {"type":"doc","version":1,"content":[...]}}`（ADF） |
